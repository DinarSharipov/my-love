# ADR 0004: opt-in idempotency для критических команд

- Статус: принято
- Дата: 2026-08-15

## Контекст

Повтор POST/PATCH после timeout или потери ответа может создать дубликат события,
первой встречи, приглашения или в будущем финансовой операции. Обязательный новый
заголовок сломал бы текущий frontend, который его пока не отправляет.

## Решение

- Команды объявляют стабильный scope через `@Idempotent` и принимают optional
  `Idempotency-Key` длиной 8–128 безопасных ASCII-символов.
- Ключ уникален в пределах пользователя и scope. В hash входят нормализованные
  body и route params; порядок ключей JSON не влияет на hash.
- Первый запрос резервирует запись на 24 часа. Успешный HTTP status и JSON response
  сохраняются и возвращаются при retry без повторного вызова use case.
- Тот же ключ с другим payload возвращает `IDEMPOTENCY_KEY_REUSED`; параллельный
  незавершённый запрос — `IDEMPOTENCY_IN_PROGRESS`.
- При ошибке use case резерв удаляется и запрос можно безопасно повторить. Если
  use case завершился, но сохранение response не удалось, reservation остаётся в
  `PROCESSING`, чтобы автоматический retry не создал дубликат.
- Сейчас механизм включён для создания приглашения, принятия приглашения, создания
  первой встречи и семейного события. Без заголовка старое поведение сохраняется.

## Ограничение и развитие

Общий HTTP interceptor не может атомарно объединить произвольную domain transaction
и сохранение response. Для будущего ledger финансовая команда обязана записывать
операцию и idempotency result в одной Prisma transaction; эта таблица и коды ошибок
остаются общим контрактом. Просроченные записи будет удалять scheduled job этапа 0.
