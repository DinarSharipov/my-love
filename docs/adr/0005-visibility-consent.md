# ADR 0005: visibility и consent для чувствительных данных

- Статус: принято
- Дата: 2026-08-16

## Контекст

Финансы и wellbeing содержат личные данные, которые нельзя автоматически открывать
партнёру только из-за общего family membership. При этом универсальная таблица с
`resourceType/resourceId` не может обеспечить внешние ключи и легко создаёт висячие
grants или случайное расширение доступа.

## Решение

- Общий словарь видимости: `PRIVATE`, `PARTNER`, `FAMILY`.
- `PRIVATE` доступен только владельцу. `PARTNER` и `FAMILY` требуют active membership
  actor и ресурса в одной семье. Пока child accounts отсутствуют, `FAMILY` и `PARTNER`
  дают одинаковый read-доступ, но остаются разными продуктовым намерением.
- Владелец ресурса задаётся сервером из текущей сессии и не меняется обычным update.
  Клиентские `ownerId`/`familyId` не считаются доказательством доступа.
- Изменение visibility — отдельная команда владельца с audit event. Нельзя расширить
  доступ через общий PATCH ресурса или команду партнёра.
- Для особенно чувствительных ресурсов (`CheckIn`, assessment, медицинские заметки)
  одной visibility недостаточно. Read policy дополнительно требует active consent grant
  с allowlisted scope, `grantedAt`, optional `expiresAt` и nullable `revokedAt`.
- Отзыв consent применяется немедленно: read path проверяет актуальный grant в БД,
  а projection/cache не может продлевать доступ. Изменения grant аудитируются без
  свободного текста, ответов assessment и медицинского содержимого.
- Grant хранится в модуле-владельце чувствительного ресурса со строгим foreign key.
  Общая polymorphic consent-таблица до появления первого потребителя не создаётся.
- При выходе из семьи или её расформировании доступ не-владельца прекращается через
  active-membership check. Данные владельца и история consent сохраняются по retention
  policy соответствующего домена.
- Dashboard, notifications, audit и exports используют ту же read policy и не являются
  обходным каналом для скрытых значений.

## Последствия

Финансовый домен может использовать visibility для personal/family wallet, но личные
суммы не попадают партнёру без разрешённой видимости. Wellbeing обязан добавить свою
FK-backed consent model и scoped policy. Общий код содержит только словарь и чистую
проверку базовых invariants; persistence остаётся типизированным внутри домена.
